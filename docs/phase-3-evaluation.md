# Phase 3: repository-aware AI and quality evaluation

**Date:** 2026-10-23. **Model:** `qwen2.5-coder:3b` via Ollama 0.40.6, temperature 0, GTX 1650
4 GB (performance mode, plugged in). No other model was benchmarked: downloading candidates was
declined, and paid APIs are out of the ₹0 budget. Raw results:
`evaluation/reports/experiments/phase3/` (one folder per run, `SUMMARY.md` generated by
`evaluation/scripts/summarize_phase3.py`). All runs are label-blind.

## 1. What changed

| Area | Change | Where |
|---|---|---|
| Held-out dataset | **v2**: 17 cases (12 defects, 5 clean). 4 multi-file defects whose proof is in another, unchanged file (units, argument order, `None` return, documented `KeyError`); realistic single-file bugs; security (path traversal, pickle, unverified JWT); clean traps including 2 correct multi-file calls. Written before any Phase 3 change and never used to tune | `evaluation/datasets/v2/cases.py` |
| Read-only tools | Search symbols, read snippets, follow calls and find call sites, confined to the review's snapshot (the exact commit), no execution, file and size budgets | `backend/app/ai/tools.py` |
| Repository-aware context | `DEVPILOT_LLM_CONTEXT=repo` adds definitions the changed code calls and other files' call sites of changed functions, marked RELATED, at most 8 snippets and 25% of the context budget; findings may cite them and are validated as before | `backend/app/ai/context.py` |
| Prompt v2 | Review procedure for calls, boundaries, time, security; RELATED contract; `unconfirmed` outlet instead of guessing | `PROMPTS["v2"]`, `DEVPILOT_LLM_PROMPT_VERSION` |
| Output schema | `unconfirmed: list[str]` (suspicions, never stored as findings) | `backend/app/ai/schema.py` |
| Telemetry and UI | Each review records prompt version, context mode, related code and unconfirmed notes; the review page shows them | `services/review.py`, `ReviewPage.tsx` |
| Harness | Records prompt version and context per run; `run_phase3.sh` grid with GPU cool-downs | `evaluation/scripts/` |

**Not done in this phase (deliberately):** tool 4 (propose a diff) and tool 5 (run tests or
checks in isolation). Running repository code needs a real sandbox (container, no network,
CPU/memory/time limits), which is its own piece of work. Model-driven tool calling was not
attempted: a 3B model cannot drive it reliably, so the tools are called deterministically.

**Source of truth, staleness and isolation:** context is built from the review's own snapshot
directory, which is the commit under review (for GitHub imports, the recorded SHA). Nothing is
cached between reviews, so a new commit can never be served old context. The tools cannot read
outside that directory (tested), so no other user's or repository's code can enter a prompt.

Recall = defects found / defects present; precision = true findings / all findings; "clean FP" =
share of clean cases with any finding; `ai_failed` = cases whose model call failed (counted as
failures, never as zero findings).

Cost: ₹0 for every run (local inference; electricity not counted). Correctness of explanations
and patch validity could only be judged on the single model finding: its explanation names the
missing-flag `KeyError` path correctly. No patch was applied or tested (tool 5 not built).

### What the numbers say

1. **v1 overstated the analyzers.** 9/13 on v1 fell to 2/12 on the held-out v2. The v1 rules were
   chosen while looking at v1; v2 is the honest estimate (still small and synthetic).
2. **The 3B model barely reviews.** Across 8 configurations it returned an empty findings list on
   almost every case (mean 24 to 51 output tokens, summaries such as "No findings"). It also left
   `unconfirmed` empty everywhere, so prompt v2's outlet did not reveal hidden suspicions.
3. **Repository context was delivered but not used.** The dry run and the per-case telemetry show
   the right definition reached the model in all 6 multi-file cases (`related_code` = 1), yet
   multi-file recall stayed 0/4 with it. The model's one valid finding came without it.
4. **The one model contribution is real but thin.** `mf-unhandled-keyerror` was found in both
   runs with prompt v1 and changed-only context (deterministic at temperature 0), and in neither
   prompt v2 nor repo-context run. One case is not evidence that v1 is better than v2 in general.
5. **No false positives anywhere**, from analyzers or model, on 9 clean cases across both sets.

## 3. Decision (release gate)

- **Production stays on prompt v1 with changed-files context** (`DEVPILOT_LLM_PROMPT_VERSION=v1`,
  `DEVPILOT_LLM_CONTEXT=changed`), the defaults. It is the only configuration that measured any
  gain (3/12 vs 2/12 on v2) and costs the fewest tokens. Prompt v2 and repo context are **not**
  shown to be better and are not enabled. They remain available as settings for a stronger
  model, where the mechanism (verified delivery of the right definitions) can be re-measured.
- **Production provider/model:** Ollama with `qwen2.5-coder:3b`, kept as an optional assistant.
  The analyzers carry the product; the model adds at most one finding in twelve on held-out data.
- **Release gate status:** backend 124 passed (4 opt-in live tests deselected), ruff, format,
  mypy, bandit clean; frontend 7 unit tests, typecheck, build, 2 Playwright end-to-end passed,
  eslint 0 errors (5 pre-existing warnings). Evaluation numbers above are reproducible with
  `bash evaluation/scripts/run_phase3.sh` from `backend/`.

## 4. Limitations

- One model only; no larger or hosted model was measured, so the context improvements are
  verified mechanically, not shown to raise quality.
- Single run per configuration. At temperature 0 the repeated configuration (v2, prompt v1,
  changed) gave identical results, but other noise sources (GPU, driver) are not ruled out.
- Both datasets are synthetic and written by the tool's authors; 12 to 13 defects per set means one
  case moves recall by about 8 points.
- Related-code retrieval is Python-only and name-based (no type resolution); names defined in more
  than two places are skipped as ambiguous.
- Tools 4 and 5 (diff proposal, sandboxed test runs) are not built.

## 5. Next steps (in order)

1. Measure a stronger model on v2 through the existing provider abstraction (for example
   `qwen2.5-coder:7b` locally if a download is approved, or Claude if a budget appears), with
   prompt v1/v2 and both context modes. Enable repo context only if multi-file recall improves.
2. Grow v2 with real-world bugs from public fix commits (with licences recorded) to reduce
   authorship bias.
3. Build the sandbox for tool 5 before any "run tests" feature.
